# 0007. 인증은 core-api가 JWT를 직접 발급한다

상태: 제안 (2026-11-09. auth 담당 A가 승인하면 채택)

## 맥락

DB로 Supabase를 쓰기로 했으니(0005) 인증도 Supabase Auth에 맡기는 선택지가 있었다. 비밀번호 해시와 토큰 발급을 직접 하지 않아도 된다.

MVP의 인증 범위는 좁다. 회원가입 없음(seed 계정), 학생·교수·관리자 로그인 3종, JWT 1시간 만료, 비밀번호 재설정 없음, 소셜 로그인 없음. API 명세 V1에는 `/auth/{student|professor|admin}/login`이 이미 정의돼 있고 프론트가 이 기준으로 작업 중이다. Must 완료 기준은 docker compose만으로 전체가 뜨는 것이다.

## 결정

core-api가 JWT를 직접 발급한다. 비밀번호는 bcrypt, 토큰은 1시간 만료, 역할은 토큰 클레임에 넣는다. Supabase Auth는 회원가입과 학교 이메일 인증(C3)이 범위에 들어올 때 다시 검토한다.

Supabase Auth를 지금 쓰지 않는 이유:

- 관리형 인증의 장점(가입, 인증 메일, 재설정, 소셜 로그인, MFA)이 MVP 범위에 하나도 없다. 남는 장점은 해시를 안 하는 것 정도인데 Spring Security에서 한 줄이다.
- 공식 로컬 개발 방법은 Supabase CLI 전체 스택이다. Auth 서버(GoTrue) 컨테이너만 따로 띄울 수는 있지만 문서화된 경로가 아니고 설정 부담이 크다. 어느 쪽이든 "compose 한 번으로 전체가 뜬다"는 기준과 부딪힌다.
- 역할 3종을 토큰에 넣으려면 Auth Hook이나 admin API로 `app_metadata`를 써야 하고 seed 계정도 Supabase Auth에 스크립트로 만들어야 한다. 로그인 API 3개를 만드는 것보다 설정이 많다.
- API 명세, 프론트 로그인 흐름, core-api `auth` 도메인을 동시에 바꿔야 한다. 세 팀의 작업이 늘어난다.

## 결과

- API 명세 V1과 프론트 작업을 그대로 둔다. 로컬에서 인증까지 완결된다.
- 감수할 것: 비밀번호 해시와 토큰 발급·검증 코드를 직접 책임진다. 기획서 보안 지표(bcrypt, 1시간 만료)가 코드 리뷰 항목이다.
- 감수할 것: 토큰 갱신이 없어 1시간 뒤 재로그인한다. 과제 제출 중 만료되면 프론트가 안내해야 한다.
- C3를 당기면 이 결정을 새 ADR로 대체한다.
