# 0009. 서버는 레포 하나에 서비스별 폴더, 클라이언트는 별도 레포

상태: 채택 (2026-11-06, 기획서 v0.6)

## 맥락

서비스가 core-api, judge-worker, lint-worker, web으로 나뉘고, 채점 컨테이너 이미지 judge-image가 따로 있다(0001). 저장소를 어떻게 나눌지 정해야 한다. 서비스마다 레포를 두면 배포 단위와 레포가 1:1이라 깔끔하지만, 큐 메시지 정의(`contracts/`)처럼 서비스가 함께 보는 것을 어디에 둘지, PR 하나로 보내는 쪽과 받는 쪽을 같이 고치는 규칙을 어떻게 지킬지가 문제가 된다. 서버 담당은 2명이다.

## 결정

서버 서비스 3개와 judge-image는 `server` 레포 하나에 폴더로 둔다. 각 폴더는 독립 Gradle(또는 Python) 프로젝트이고 서로 import하지 않는다. 클라이언트(web)는 `autota-web` 레포로 분리한다.

- 서버를 한 레포에 두는 이유: 큐 메시지 정의와 그 변경이 한 PR 안에서 양쪽 서비스와 함께 움직여야 한다. 레포를 서비스마다 나누는 것은 담당 조직이 갈리는 규모에서 할 일이다(기획서 8절).
- 클라이언트를 나누는 이유: 정적 자산이라 빌드·배포 주기가 다르고, 담당 팀이 다르다.

## 결과

- `contracts/` 변경과 송수신 양쪽 수정을 PR 하나로 묶는 규칙(`docs/conventions/git-convention.md` §2)이 가능하다.
- 커밋 scope를 서비스 또는 도메인 단위로 잡는 컨벤션이 여기서 나온다.
- 감수할 것: CI는 서비스별 워크플로에 `paths:` 필터를 걸어 바뀐 서비스만 돌린다. 필터로 건너뛴 워크플로는 결과가 없어 브랜치 보호의 필수 체크로 걸 수 없다(git-convention §4).
- 감수할 것: 서비스별로 빌드 도구·런타임이 달라 레포 루트에서 한 번에 빌드하는 명령이 없다. 로컬 전체 기동은 `docker-compose.yml`이 맡는다.
- 감수할 것: 클라이언트와 API 계약은 레포가 달라 Notion API 명세와 springdoc 산출물로 맞춘다.
