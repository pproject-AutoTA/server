# 0001. 서비스 간 통신은 큐 메시지로만 한다

상태: 채택 (2026-11-06, 기획서 v0.6)

## 맥락

서비스는 따로 배포하거나 따로 확장할 이유가 있는 단위로 나눴다. core-api는 상시 가동이고 부하 변동이 완만하다. 채점은 제출이 몰릴 때만 부하가 튀고 격리가 필요하다. 허용 요소 검사는 격리가 필요 없고 짧게 끝난다. 이렇게 나누면 서비스끼리 어떻게 부를지 정해야 한다.

채점을 HTTP로 동기 호출하면 마감 직전에 제출이 몰릴 때 core-api가 채점이 끝날 때까지 붙잡혀 API 전체가 느려진다.

## 결정

서비스는 RabbitMQ 큐 메시지로만 통신한다. core-api가 `judge.queue`·`lint.queue`에 넣고, 워커가 꺼내 처리한 뒤 `result.queue`로 돌려보낸다. 워커는 core-api를 호출하지 않고 HTTP API도 두지 않는다(헬스 체크만 예외). 메시지 필드 정의는 `contracts/`에 두고 각 서비스가 복사해 쓴다.

## 결과

- 의존이 core-api → 큐 → 워커 → 큐 → core-api 한 방향이라 워커를 바꾸거나 늘려도 core-api가 영향을 받지 않는다.
- 제출이 몰려도 큐에 쌓였다가 처리되므로 API 응답은 바로 돌아간다.
- 감수할 것: DB 저장과 큐 발행이 한 트랜잭션이 아니다. 발행 실패 시 제출이 '대기'에 남는 문제의 처리 방식은 아직 정하지 않았다(`docs/architecture.md` §1).
- 감수할 것: 큐는 at-least-once라 결과 수신은 `(submission_id, 결과 종류)` 기준으로 멱등해야 한다.
- 감수할 것: 서비스 간에 코드를 공유하지 않으므로 메시지 record를 서비스마다 복사하고, 변경은 `contracts/` 규칙대로 한 PR에서 양쪽을 고친다.
