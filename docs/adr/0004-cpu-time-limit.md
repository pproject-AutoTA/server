# 0004. 시간 제한은 CPU 시간으로 판정한다

상태: 채택 (2026-11-06, 기획서 v0.6)

## 맥락

채점 노드는 B시리즈 버스트형이다. 크레딧이 남아 있을 때는 CPU를 다 쓰지만, 소진되면 기준선 성능으로 조여진다. 제출이 몰리는 마감 직전이 크레딧이 떨어지는 시점이기도 하다. 동시에 도는 Job끼리도 서로 간섭한다.

벽시계 시간(wall-clock)으로 재면 같은 코드가 평소에는 통과하고 몰릴 때는 TLE가 된다. 기획서 성공 지표 "같은 제출 10회 재채점 시 판정 일치"를 못 지킨다.

## 결정

시간 제한은 프로세스가 실제로 CPU를 쓴 시간(user + sys)으로 판정한다.

- **측정**: 실행 스크립트가 학생 프로세스를 실행하기 전후의 컨테이너 cgroup `cpu.stat`(`usage_usec`) 차이를 CPU 시간으로 삼는다. 학생 코드가 프로세스를 여러 개 띄워도 합산되고, 단위가 µs다. cgroup v2를 전제로 한다(Docker Desktop 기본값, AKS Ubuntu 24.04 노드). cgroup v1 호스트에서 개발하는 사람은 Docker 설정을 v2로 맞춘다. 스크립트 자체의 사용량은 대기뿐이라 무시할 수준이다.
- **강제 종료**: `RLIMIT_CPU`는 초 단위 정수이고 프로세스별 한도라 판정 기준으로는 못 쓴다. 제한값을 올림한 뒤 1초를 더한 값으로 걸어 **안전장치**로만 쓴다. 판정은 위 측정값으로 한다.
- **제한값**: Must(M3)에서는 교수가 문제마다 직접 입력한다. S4부터는 모범답안 실행 시간의 배수를 기본값으로 제안한다.

## 결과

- 노드가 조여지거나 옆 Job이 CPU를 써도, 이 코드가 한 일의 양은 같으므로 판정이 같아야 한다.
- 감수할 것: `sleep`이나 입출력 대기만 하는 코드는 CPU 시간이 쌓이지 않아 끝나지 않는다. 벽시계 기준 안전 상한(예: CPU 제한의 몇 배)을 따로 두고 넘으면 강제 종료한다. 이 경우도 TLE로 기록한다.
- 감수할 것: `RLIMIT_CPU`는 soft 한도에서 SIGXCPU, hard 한도에서 SIGKILL을 보내며, 핸들러가 있으면 커널이 soft 한도를 1초씩 올린다. 그래서 안전장치는 soft = hard로 걸고 핸들러를 두지 않는다.
- 감수할 것: 조여진 VM에서 게스트 커널이 CPU 시간을 정확히 세는지는 검증하지 않았다. 크레딧이 찬 상태와 소진된 상태에서 같은 코드를 재채점해 측정값을 비교한다(`docs/architecture.md` §4). 어긋나면 채점 노드를 B시리즈가 아닌 SKU로 바꾸는 것을 검토한다.
